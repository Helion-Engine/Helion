# Build Instructions

## Windows

If using **Visual Studio 2022+** or **Rider**, press Run and it will do everything.

## Linux

Install dependencies first:

### Debian/Ubuntu

```sh
sudo apt install dotnet-sdk-10.0 libopenal-dev
```

If you want to do AOT builds (see section below), you will also want:
```
sudo apt install libsndfile1-dev libmpg123-dev libglib2.0-dev libasound2-dev
```

Then go to the "Command Line Build" section below.

### Fedora

```sh
sudo dnf install dotnet-sdk-10.0 openal-soft-devel
```

Similar to Debian/Ubuntu, you will also want dev packages for AOT:
```
sudo dnf install libsndfile-devel mpg123-devel glib2-devel alsa-lib-devel
```

After installing dependencies, if you have an IDE that supports C# (like Rider), you can open Helion and build/run directly.  You can also build from the command line, as described in the section below.

Note that we have provided copies of various binaries we depend upon.  If you experience difficulties using the provided .so files, you may need to build your own. Symptoms may include nonfunctional music, or issues with controller input.  Please see link:Assets/Documentation/Building-Linux-Native-Dependencies.md[this document] for help with native dependencies.

## Mac

M-series ARM64 Macintosh is supported. Intel-based Macintosh machines are not supported, nor do we intend to do so in the future.  Status of ARM64 other than M-series (e.g. Macbook Neo with A18 Pro SoC) unknown and untested.

If you wish to build Helion on an ARM Mac, you will need to install link:https://brew.sh/[Homebrew].  Then `brew install --cask dotnet-sdk`.

If you wish to do AOT builds (see explanation below) on Macintosh Arm64, you will need to run `brew install libsndfile mpg123 glib` to get the necessary `.a` files for linking.  Clang must also be installed on your system (it seems to be present by default on OS 26.x).  Note that these steps are ONLY necessary for AOT builds.

## Command Line Build

Once any platform-specific prerequisites are installed, you can build or publish using the `dotnet` commands available with the .NET SDK.  By default, `dotnet build` will build an "any" binary that uses the installed version of the .NET runtime.  This is mainly intended for local debugging.  

.Publishing
The `dotnet publish` command provides various options to package Helion for use on other machines, including ones that do not have the runtime installed.  We recommend this if you just want to play the game, especially if you want to use it on a machine other than the one you are building it on.

First `cd` to the `Client` subdirectory (this is the only one that builds an executable, and thus the only one eligible for publishing).  If you want to do a "normal" build (see section below), run `dotnet publish -c Release -r <runtimeID> -p:SelfContainedRelease=true`.  If you would like an "AOT" build, run `dotnet publish -c Release -r <runtimeID> -p:AOT=true`.  Note that AOT builds require a native linker (provided by Clang or GCC on Linux, Clang on MacOS, or a full install of Visual Studio on Windows), and must be run ON the target platform (you cannot do a Linux AOT build from Windows or Mac, for example).

We support the following runtime IDs:
* osx-arm64
* linux-x64
* win-x64

Your build will be published to a subdirectory `(repo root)/Publish` with a name depending on the parameters you specified (e.g. `linux-x64_AOT`)

## AOT and "Normal" builds

The .NET SDK normally builds assemblies (libraries or programs) that require Just-In-Time (JIT) compilation when run.  This is largely transparent to the user, but can result in long startup times.  However, it provides some "self tuning" capability as the application recompiles on the fly and optimizes for "hot" code paths.  Additionally, JIT compilation can use the _exact_ instruction set and extensions supported by the user's system. See link:https://github.com/dotnet/runtime/blob/main/docs/design/features/tiered-compilation.md[Tiered Compilation in the .NET documentation] for more information.

.NET Native Ahead-Of-Time compilation, or "AOT", is a more traditional approach that compiles a native executable that does not require JIT.  This often results in a smaller executable, faster startup, and performance characteristics that remain consistent.  It also provides (and Helion uses) Direct P/Invoke, which allows linking to dependent libraries.  This can be especially desirable for portability and packaging on *NIX environments since it honors normal loader semantics such as RPATH, LD_LIBRARY_PATH, etc.  The downside is that the "self tuning" capability of JIT is gone, and a "lowest common denominator" target architecture must be chosen at compile time.  Unless overridden with `-p:IlcInstructionSet=<some specific revision>`, this means that x86-64 applications will not use newer instruction set extensions, such as newer versions of Intel SSE.  See link:https://github.com/dotnet/runtime/blob/main/src/coreclr/nativeaot/docs/optimizing.md[Native AOT optimization in the .NET documentation] for further details.

Cross-platform compilation is possible on normal builds, but not for AOT, as the .NET SDK does not provide a mechanism to use a cross-platform toolchain (such as mingw on Linux).

We recommend trying both normal and AOT builds and then sticking with whichever provides the performance characteristics you prefer.  Non-AOT builds may offer a performance advantage on highly CPU-constrained systems, at the cost of a slower startup, higher memory usage, and initially lower performance which will improve as JIT compilation performs optimizations on-the-fly.  AOT builds start instantly, but lack the self-tuning capabilities of JIT.
